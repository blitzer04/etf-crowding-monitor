# Repository Guidelines

## Project Purpose

This repository is the **U.S. ETF Crowding & Overheating Risk Monitor**, a quantitative-finance research project and public Streamlit application. Use Python 3.12. Treat methodological correctness, point-in-time data integrity, reproducibility, and clear communication of limitations as core product requirements.

## Repository Organization

Keep responsibilities separated by directory:

- `src/etf_crowding/`: production package code and all reusable calculations.
- `tests/`: automated tests, organized to mirror package behavior.
- `docs/`: research methodology, data definitions, and limitations.
- `notebooks/`: exploratory analysis only; never the sole home of reusable logic.
- `scripts/`: command-line data, maintenance, and research workflows.
- `app/`: Streamlit pages and presentation code.
- `data/raw/`, `data/processed/`, and `data/snapshots/`: clearly separated data stages.

The Streamlit application must call package functions from `src/etf_crowding/`; do not duplicate financial logic in `app/`. Keep exploratory notebook code separate from production code.

## Python Engineering Standards

- Write simple, explicit Python that looks carefully authored and maintained. Prefer readability over clever abstractions or micro-optimizations.
- Use descriptive function and variable names. Add type hints to public functions and important internal functions.
- Give functions one clear responsibility. Split giant functions and files along meaningful domain boundaries.
- Do not create generic dumping-ground modules such as `utils.py`. Name modules for their domain responsibility, such as `flow_proxies.py` or `concentration.py`.
- Use `pathlib.Path` for filesystem access instead of hard-coded path strings.
- Use structured `logging` for pipeline status and diagnostics, not scattered `print` statements.
- Use vectorized pandas operations when they improve clarity. Do not make code harder to read for marginal performance gains.
- Do not introduce machine learning unless explicitly requested.
- Avoid unnecessary classes, design patterns, and dependencies.
- Do not use emojis in source code or professional documentation.
- Do not add statements such as "AI generated," "generated by Codex," or similar attribution.

## Documentation and Comments

Every public module, class, and non-trivial public function must have a concise Google-style docstring. Document its purpose, arguments, returns, and any important financial assumptions. Do not add docstrings to trivial one-line private helpers merely to increase documentation coverage.

Comments should explain why a decision exists, especially for financial assumptions, data-cleaning choices, look-ahead-bias prevention, or unusual edge cases. Do not translate the next line of Python into English, and avoid excessive comments.

Keep `README.md` accurate as commands, architecture, and outputs evolve. When methodology changes, update the relevant documentation in the same task.

## Financial Data Integrity

- Never fabricate missing financial data or present fake sample results as real market results.
- Preserve missing values when a legitimate observation is unavailable, and clearly flag data-quality problems.
- Never silently forward-fill data. Forward-filling is allowed only when the documented methodology explicitly justifies it.
- Prevent look-ahead bias in every research calculation: a value at time `t` may use only information observable at or before `t`.
- Record data provenance and timing assumptions sufficiently to audit whether an input was available at the calculation date.
- Clearly document survivorship bias, data availability, proxy limitations, and look-ahead-bias controls.

## ETF Methodology Rules

- Distinguish true reported ETF flows from estimates. When flows are inferred from changes in shares outstanding, call the result a **creation/redemption flow proxy**; never describe it as an exact reported fund flow.
- Current holdings may be used for a current concentration score. Do not construct historical concentration scores from current holdings unless point-in-time historical holdings data exists.
- Use adjusted prices for total-return calculations when appropriate. If a calculation requires raw prices, document why adjusted prices are unsuitable.
- State units, date alignment, missing-data behavior, and financial assumptions near each metric's implementation or methodology documentation.

## Testing and Quality Gates

Test important formulas, transformations, and edge cases. Financial metrics must have unit tests built from small, hand-calculated examples. Tests should verify meaningful behavior rather than implementation details. Include coverage for missing observations, date boundaries, stale or malformed inputs, and cases that could introduce look-ahead bias.

After meaningful changes, run the relevant checks once the tools are configured:

```text
ruff check .
ruff format --check .
mypy src/etf_crowding app
pytest
```

Run narrower checks during iteration when useful, then execute the applicable full suite before completion. Fix warnings when reasonably possible instead of suppressing them. Never claim a check passed unless it was actually executed successfully.

## Security and Configuration

Never commit API keys, credentials, `.env` files, Streamlit secrets, or other sensitive configuration. Keep secrets in approved local or deployment-specific secret stores. Ensure logs and error messages do not expose secret values.

## Task Completion Protocol

Before completing any task:

1. Inspect the existing repository and relevant files.
2. Preserve sound existing design decisions.
3. Implement only the requested scope.
4. Run relevant formatting, linting, typing, and tests that are configured and available.
5. Summarize every file changed.
6. Report the exact checks executed and their results.
7. State unresolved limitations honestly, including unavailable data or tooling.
8. Do not create a Git commit unless the user explicitly requests one.

## Mandatory Data-Pipeline Boundary Review

Before declaring an ingestion or persistence change complete, map and audit every transformation boundary:

`provider payload -> identity/metadata validation -> raw extraction -> per-entity normalization -> per-entity validation -> batch combination -> batch validation -> existing-data load -> representation harmonization -> deduplication -> source-vintage merge -> coverage checks -> snapshot -> atomic persistence -> reload validation`

A value/dtype/schema accepted as canonical must be supported end-to-end across every operation the pipeline requires, including comparison, hashing, concatenation, missingness, finite-value checks, Parquet write, and Parquet reload.

Never assume pandas dtype promotion is lossless. Any numeric conversion that can change a financial value must be proven lossless by exact round-trip/value checks or rejected. Always test integer values above `2**53`.

Validate provider-returned identifiers before assigning requested identifiers. Do not silently relabel mismatched provider data.

Validate schemas, keys, and value dtypes before any hashing, grouping, duplicate detection, arithmetic, or serialization that assumes valid scalar inputs.

Resolve wall-clock-dependent batch defaults once per batch when reproducibility requires a common reference instant. Convert that common instant per relevant exchange/provider timezone rather than recomputing `now` per entity.

Treat process-global third-party configuration as shared mutable state. Avoid mutation where possible; otherwise use one shared synchronization mechanism across all project adapters and restore exact prior state.

Source provenance must remain monotonic under concurrent retrieval/persistence orderings. Test reversed persistence order, identical later observations, stale revisions, same-vintage conflicts, and value loss.

Persistence logic must distinguish positive observations from coverage metadata. If a successful refresh omits a previously stored observation inside confirmed coverage, do not silently preserve or delete it unless the methodology explicitly defines that behavior.

When a defect is found in one pipeline or boundary, audit the same failure class across all analogous pipelines and all earlier/later boundaries before declaring the fix complete.

Before completion, run an adversarial test matrix covering at minimum: null, zero, large integers above `2**53`, signed/unsigned integers, floating values, pandas nullable dtypes, PyArrow integer/float dtypes, unsupported numeric extensions, malformed object/list/array keys and values, reversed input ordering, mixed representations, provider-identity mismatch, date-boundary crossing, concurrency ordering, serialization round-trip, and partial/truncated provider responses where relevant.

Passing the existing test suite is necessary but not sufficient. Before a major ingestion milestone is committed, perform one independent read-only audit of the full data contract. Do not call the review "final" until that audit reports no actionable P1/P2 defects.
